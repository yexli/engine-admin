## DR-001 · 引擎单例的实例隔离推迟到 V0.9（V3.3 · 关闭 BLOCKERS B4）→ **V0.9 已兑现（见 DR-004）**

- **日期**：2026-09-29（V0.3）；**兑现**：2026-09-30（V0.9）
- **背景**：`worldBus` / `rng` / `scheduler` / 事件序号（`eventSeq`）是引擎模块级单例（沿袭天穹线上形态）。
  同一进程创建多个 `createWorld()` 时：事件总线互相可见（事件环按「世界存在才记录」收窄，但跨世界事实仍会互见）、
  随机流共享、事件 id 序号共享。V0.3 起 SDK 会被第三方游戏安装，多游戏嵌进同一进程的场景从「不存在」变成「可能」。
- **备选**：
  1. 现在就把四处单例实例化进 `createWorld`（每世界一份）；
  2. 保持单例，文档声明「一进程一世界」，隔离推迟；
  3. 保持单例，但为 `worldBus.emit` 增加 worldId 过滤。
- **裁决**：**备选 2**。V0.3 保持进程级单例，README/指南声明「一个进程一个活动世界」；实例隔离是 V0.9（Multi-World / Multi-User）的工程。
- **V0.9 兑现情况**：worldBus 与事件 id 序号已按预留路径实例化（**作用域工厂 + 全局缺省**，见 DR-004）；
  「双世界互不可见」不变量入 tests/registry.test.ts；`rng / scheduler` 按裁决语义保留为**进程级共享执行设施**
  （隔离范围收窄并已在 DR-004 声明）。
- **关联**：`WORLD-EXTRACTION-BLOCKERS.md` B4（已裁决 → 已兑现）。

## DR-002 · 包消费面 = 构建产物 dist（V3.1）

- **日期**：2026-09-29（V0.3）
- **背景**：V0.1-V0.2 期间天穹经 `@wengine/*` 路径别名直接引用引擎**源码**；SDK 化后消费面必须收敛。
- **备选**：
  1. 包 `main` 指向 `src/index.ts`（消费方各自转译 TS）；
  2. dist 为消费面（tsc 构建产物 + d.ts）。
- **裁决**：**备选 2**。引擎内部相对导入带 `.ts` 扩展名，构建经 `rewriteRelativeImportExtensions`
  重写为 `.js`——`dist` 是**可被 node 直接 import 的 ESM**，`npm pack` 产物经「解压 → 安装 →
  import → 跑通世界」四步实证。引擎 `npm test` 仍跑源码（vitest），`npm run build` 后的 dist 才是消费面。
- **后果**：引擎改码后必须先 `npm run build`，宿主（天穹）才能见到变化——**构建顺序纪律**已写入指南；
  d.ts 的类型检查依赖宿主 `skipLibCheck`（双方均已开启）。

## DR-003 · HTTP 服务器一服务器一世界；默认只绑 127.0.0.1（V0.4）→ **V0.9 注册表模式已兑现**

- **日期**：2026-09-29（V0.4）；**兑现**：2026-09-30（V0.9）
- **背景**：方案 §64 的路由是集合形状（`POST /v1/worlds`、`GET /v1/worlds/{id}`），暗示一个服务器可容纳多个世界；
  但 DR-001 刚裁决「实例隔离推迟到 V0.9」（worldBus/rng/事件序号是进程级单例）。
- **备选**：
  1. 服务器持世界注册表，多世界共存；
  2. 一服务器一世界：`POST /v1/worlds` 只能建一次，重复建回 409；路由保留 `{id}` 形状并校验匹配。
- **裁决**：**备选 2**。与 DR-001 一致——多世界共进程会跨世界互见事件、共享随机流（文档化行为），
  V0.9 以 worldId 为键隔离后再开放注册表。URL 中的 `{id}` 从 V0.4 起就是真实的路由参数（不匹配即 404），
  升级到多世界时客户端零改动。
- **V0.9 兑现情况**：`startWorldServer({ registry })` / `createWorldHttp({ registry })` 开放注册表模式——
  `POST /v1/worlds` 可多次（每世界独立作用域），`{id}` 路由形状不变（客户端零改动，兑现 DR-003 预留）；
  单世界模式原样保留为缺省。安全基线不变：默认 127.0.0.1、体上限 1 MiB、坏 JSON 400。
- **后果**：多世界 HTTP 由 registry 选项显式开启；鉴权/多租户仍留 V1.0。

## DR-004 · 作用域工厂 + 全局缺省：隔离的落地形态与 rng/scheduler 的边界（V0.9）

- **日期**：2026-09-30（V0.9）
- **背景**：DR-001 兑现时发现：天穹数百处模块级 `worldBus/rng/scheduler` 调用无法穿参改造
  （§59 第 10 条：无法保证行为不变），且 `advanceTime` 这类纯状态变更入口也会被安全启发式标记
  （与命名无关）——隔离必须**不改变既有宿主的任何调用路径**。
- **备选**：
  1. 全部单例穿参（每调用链传 scope）——天穹数百处改动，违反行为不变铁律；
  2. **作用域工厂 + 全局缺省**：`createWorldEventBus()` / `createEventSchema()` 工厂化，
     模块级导出绑定为全局缺省作用域；`createWorld({ isolated: true })`（及 WorldRegistry 强制）
     持有独立实例，时钟/运行时经可选参数注入；
  3. AsyncLocalStorage 式环境上下文——引擎须承诺 Node 运行时，破坏环境中性。
- **裁决**：**备选 2**。隔离范围：**事件总线（互不可见）+ 事件 id 序号（分域起算）**；
  `rng / scheduler` 保留进程级共享（执行基础设施，非世界状态；跨世界同时推进时确定性采样按
  「进程内交错」理解——已在本条与 README 声明，不是 bug）。
- **后果**：
  - 天穹（单世界）零改动：其世界运行在全局缺省作用域上，1716 回归全绿；
  - 引擎 `createWorld` 缺省也在全局作用域（既有测试/示例零改动）；`isolated: true` 与 WorldRegistry 是隔离入口；
  - 「双世界互不可见」三断言（事件环 / 事件 id / 总线订阅）+ 「隔离世界不进全局总线」保护断言入 registry.test.ts。
- **验证**：引擎 68 用例（+7 隔离与注册表）；天穹 1716 回归全绿；双世界 E2E 见 tests/registry.test.ts。

- **背景**：方案 §64 的路由是集合形状（`POST /v1/worlds`、`GET /v1/worlds/{id}`），暗示一个服务器可容纳多个世界；
  但 DR-001 刚裁决「实例隔离推迟到 V0.9」（worldBus/rng/事件序号是进程级单例）。

  隔离天然成立。
