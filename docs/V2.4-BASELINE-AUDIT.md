# V2.4-00 基线审计（Runtime Hardening · 只读）

> 时间：2026-10-03　基线：V2.3 发布（platform 0.20.0 / world-engine 1.2.1，四包 409 项测试全绿）
> 性质：**只审查、不大改、不重构**（方案 §四）。结论按 15 问逐条给出证据（文件:行号）与风险等级。
> 风险等级：P0 = 破坏世界正确性｜P1 = 运行异常｜P2 = 可维护性/可观察性｜P3 = 优化项。

## 一、15 问逐条裁定

### Q1 Event 是否真正持久化？——❌ 否（**P1** → V2.4-01）
引擎事实只存于进程内环形窗口（200 条）+ SavePort。持久化接口 `SavePort.loadWorldLog/saveWorldLog` 与两个介质实现**已存在但 src 内零调用**（grep 证实，P0 审计 §一.6 与本次复核一致）。进程重启 = 世界事件史全失（状态可持久，事件不可）。

### Q2 重启后 Event 是否存在？——❌ 否（P1，随 Q1）
引擎重启后 `GET events` 仅能返回新实例的事件（且事件 id 按世界实例从头计数——多代语义见 Q5）。

### Q3 Event 可 Replay / Recovery？——❌ 缺失（P2 → V2.4-01 尾部）
无重放机制。部分替代：Memory（P7）与 Evolution Journal（P1）各自持久化并跨重启恢复，但「世界事件流本身」不可恢复。

### Q4 EvolutionRun 与 Event 是否直接关联？——✅ 是
`ChangeOutcome.eventIds`（types.ts:223）记录每条 change 产生的事实 id；因果链端点（P9）八环还原 Event→Trigger→Context→Model→Proposal→Validation→Command→Mutation→New Events；测试钉住（admin-runtime/world-schema/evolution-v2）。

### Q5 Trigger 是否可能重复唤醒？——✅ 已防（残留窗口受控）
三层：消费 seen 集合（consumer.ts:45）、演化幂等键含代际 `auto:{world}:{gen}:{event}:{npc}`（P9）、世界重建指纹检测自动重置（P9）。**残留窗口**：指纹每 N 轮（缺省 10）比对一次，世界重建后最坏 ≤ N×interval 的触发被误判重——有界、自愈，P3 记录。

### Q6 NPC Tick 是否可能重复执行？——✅ 已防
同一世界并发 tick 串行锁（P1）；个体决策幂等键按 `world|gen|event|npc` 分域；冷却按 `world|focus` 分域。测试钉住（extensions/evolution-p1-closure）。

### Q7 Scheduler 是否存在多来源？——⚠️ 双源但幂等（P3）
平台 ScheduleRuntime（权威循环）与宿主启动/输入时立即对齐并存。对齐按「权威状态 vs 日程」比对、已对齐零命令——竞态只会多读一次状态，不会重复移动。已文档化（scheduler.ts 头注）。P3 记录：长期应收敛为单源。

### Q8 Runtime 是否已成 God Object？——⚠️ 中度（P2 → §十五分阶段拆）
`evolution/runtime.ts` 437 行（闭环 + 幂等账 + 焦点作用域 + 记忆召回钩子 + 因果 trace）；trigger/schedule/memory runtime 各 186–271 行职责单一。按方案 §十五：先稳定行为，不立即拆。P2 记录拆分路线（runtime/ 子目录方案）。

### Q9 Memory 是否可追溯来源 Event？——✅ 大部分（P2 小缺口 → V2.4-07）
`MemoryEntry.sourceEventId` 摄取时写入（world-memory engine.ts:61,79）；**缺口**：`recallFor` 投影 {ref, summary, day} **丢弃 sourceEventId**，context.memory 段与因果链无法闭环「这句话为什么知道」。补投影即闭环（小改）。

### Q10 AI Proposal 是否存在绕过 Rules 的路径？——✅ 无（结构保证）
EngineClient 接口只有 proxy/getState/getEvents/executeCommand——不存在状态写方法（types.ts:123-142）；触发分级/围栏/翻译三层拒绝 + 金币键禁令（P5）；worldagent 管线只读。源码扫描断言钉住（integration.test）。

### Q11 Command 是否具备幂等能力？——❌ 引擎层缺失（**P1**）
引擎命令契约无 idempotencyKey（sanitizeCommand 白名单外字段一律剥除）；HTTP 重试 = 重复 Mutation（金币扣两次/移动两次）。平台演化命令已有三层幂等（P1），但**游戏方普通命令**（如宿主经济四连命令）无引擎级防重。→ V2.4 补：命令幂等键（additive）或宿主重试纪律文档化。

### Q12 多 Proposal 同时修改同一 Entity 如何处理？——⚠️ 串行化、无版本冲突检测（P2）
同一世界 tick 串行锁（P1）；不同 tick 先后执行时后到者基于**最新状态**评估（不静默覆盖旧提案——每次都是独立判断 + Rules 终审）。缺实体/状态版本字段，无法检测「基于过期观察的写入」。方案 §十六接受第一阶段串行语义；版本化列 V2.5。

### Q13 World Time 是否可能倒退？——✅ 单调
`advance(n)` 仅 `s.t++` 逐刻推进（WorldClock.ts:169-171），无任何回退路径；HTTP 端点校验 ticks ≥ 1；恢复时 t 随档。世界重建重置 t 属多代语义（P9 文档化）。

### Q14 Entity 删除后是否存在悬空引用？——❌ 是（**P1** → V2.4-02）
`removeEntityRule`（coreRules.ts:44-58）仅 `delete npcs[id]`，**不清理**：① 世界关系表中该实体相关边；② 其他实体 `rels` 边；③ 记忆（owner/entities 含该 id）；④ 他人 `attention` 指向。悬空引用会导致唤醒评估/上下文构建引用不存在实体。V2.4-02 不变量工作首要项。

### Q15 Admin 能否追踪一次完整 AI 演化？——✅ 能（P9）
因果链八环 live 可查（trace 端点）；观测面 `/v1/admin/runtime` 单点聚合；预算报告/wakePlan/记忆段/goal 段全部入账 run。

## 四、结论

15 问中 **8 问已达成**（多数由 V2.3 的 P1–P9 工作提前覆盖）、**3 项 P1 级缺口**（事件持久化、命令幂等、删除悬挂）与 3 项 P2。V2.4-01（Event Persistence）为第一优先级，与方案一致。审计阶段未修改任何代码。
