## 1. 分类一 · 纯函数 / 表现契约型（**不该事件化**）

合计 **32 条边**（Money 8 + Derived 7 + Sheet 12 + Naming 3 + 部分 Equip / Diplomacy）。

- `economy/Money`：`formatMoney` 是字符串格式化。
- `character/Derived`：`maxHp` / `AC` / `mod` / `xpNeed` 是纯计算，无副作用。
- `character/Sheet`：`openDialog` / `confirmSheet` 是**表现层浮层描述符**，给 UI 看的，不是世界状态。
- `naming/Naming`：随机取名，无状态。

**为什么不该事件化**：把 `formatMoney` 改成「发事件 → 订阅者格式化 → 回传字符串」是反向优化——链路变长、调试变难、收益为零。这类调用是**共享工具函数**，正确形态就是直接 import。

## 2. 分类二 · 只读查询型（**可保留**，按需收敛）

合计约 **20 条边**（Equip 的 `critRate`/`instMods`、Factions 的 `repAxis`/`factionName`、Codex 的 `codexStats`、Bond 的 `bondOf`/`grudgeOf`、Quests 的 `canTurnIn` 等）。

它们读数据用于判断，不改状态，不构成 §21 的实质违反。收敛路径是改经 `world.query`（一期已给 UI 侧做过同样的工作），优先级低。

## 3. 分类三 · 状态影响型（**应事件化清单**）

合计约 **18 条边**，集中在 5 个模块的**写函数**上：

| 生产方 | 写函数 | 目标事件（建议名） | 消费方 |
|---|---|---|---|
| 多处 | `Npcs.adjAtt` | `relationship_changed`（**已存在**） | 关系系统自己订阅 |
| 多处 | `Npcs.addMem` | `npc_memory_written` | memory 引擎 |
| 多处 | `Factions.adjRepAxis` | `reputation_axis_changed` | faction 订阅 |
| Combat / Chat / Title | `Codex.deepTalkUnlock` / `readTome` | `lore_unlocked` | codex 订阅 |
| Dialogue / ActionParser | `Bond.setGrudge` | `grudge_formed` | relationship 订阅 |
| ActionExecutor / Dialogue / Craft | `Law.commitCrime` | `crime_committed`（**已存在**） | law 订阅 |
| Chat | `Relations.spreadRumor` | `rumor_spread` | relationship 订阅 |

改造范式照抄已有的三条实例（`Combat → character_died → quest 订阅`）：生产方发事件、消费方在 `subscriptions.ts` 注册。注意两条约束——**派发顺序**（通配订阅者先于具体类型）与**订阅幂等**（`processedBy` 按 owner key 记账，同一系统多事件要合并进一次 `subscribe()` 调用）。

## 4. 一个与方案预设不同的判断

`character/Gains` 有 **20 条边**（全仓最多），按被依赖度排序本该排在改造首位。**但它不该事件化**：

一期之后 `Gains` 已经是 `world/mutate` 的薄封装——它的角色从「系统实现」变成了「世界状态的写入 API」。把它事件化意味着「给玩家 10 金币」要走「发事件 → character 订阅 → 加钱」，是把 **API 调用**降级成异步消息，与分类一的理由完全相同。

真正需要事件化的是**跨系统语义通知**（A 的行为导致 B 的状态变化），而不是**共享写入 API**。这条区分是本报告的核心结论，也是「不分类就改造」会踩的坑。

## 5. 与 §21 铁律的关系（诚实结论）

改造完清单里的 18 条之后：

- 状态影响型 → 事件化：**达成**
- 只读查询型 → 保留直调（不改状态，不构成实质违反）
- 纯函数型 → 保留直调（正确定位就是共享工具）

也就是说 `src/systems` 内部的 import **不会归零**（预计剩 80 条左右），但**「系统 A 直接改系统 B 的状态」这一实质问题会消失**。这与一期复核里「102 条一条未减」的计数口径不同——请以本报告的分类口径为准。

## 6. 下一步（H-09 的执行顺序）

按被依赖度**从低到高**改造（先做边数最少的，风险最小），每个模块一个 commit：

## 7. 执行结果与一处修正（H-09 落地后补记）

### 已事件化：4 个写函数、5 处调用点

| 原写函数 | 新事件 | 生产方改动 |
|---|---|---|
| `Codex.deepTalkUnlock` | `lore_unlocked`（mode: deep_talk） | `Chat.ts` 改 emit |
| `Codex.readTome` | `lore_unlocked`（mode: read_tome） | `Combat.ts` 改 emit |
| `Bond.setGrudge` | `grudge_formed` | `ActionParser.ts` ×2、`Dialogue.ts` ×2 改 emit |
| `Relations.spreadRumor` | `rumor_spread` | `Chat.ts` 改 emit |

消费侧在 `subscriptions.ts` 注册。注意 `subscribe()` 是**覆盖式**注册——codex 与 relationship 各只能调一次，多事件类型必须合并进同一次调用（codex 用 `data.mode` 分派，relationship 用 `e.type` 分派）。

### 修正：§3 清单里的四条应当剔除

原清单把 `Npcs.adjAtt` / `Npcs.addMem` / `Factions.adjRepAxis` / `Law.commitCrime` 也列为应事件化。**执行时按 §4 的判据把它们剔除了**——它们是**世界状态的写入 API**（改好感、写记忆、调声望轴、记犯罪），与 `Gains` 同类：事件化等于把 API 调用降级成异步消息。

值得一提：`adjAtt` / `commitCrime` 这类函数**本来就会在状态真的变化时发布事实事件**（`relationship_changed` / `crime_committed`）。也就是说「跨系统语义通知」这一层它们早已具备——消费方要反应，订阅那个事实即可，不需要把写入本身也事件化。

§3 与 §4 的口径在这一点上原先不一致，本节的剔除是对齐后的结果。

### 守卫

`arch-infra` 新增用例「事件化后的写函数不得再被 systems 目录直调」：扫描 `src/systems/**` 的 import 语句，出现 `deepTalkUnlock` / `readTome` / `setGrudge` / `spreadRumor` 即红。

### 剩余与预期

`Factions.adjRepAxis`（6 条边）按上述修正**保留直调**。因此 `src/systems` 内部的 import 总数不会归零——这是分类口径下的预期结果，判据见 §5。
