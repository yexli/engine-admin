## 1. 先看清成本在哪（这一步别跳）

我按当前实现逐个量过，结论可能与直觉相反：

| 热点 | 现状 | 200 NPC 时 | 结论 |
|---|---|---|---|
| **记忆衰减** | `memoryTick` 每天遍历**全部 owner × 全部记忆** | 200 × 80 = **16000 条/天** | **最大杠杆** → Phase 6 |
| **全量序列化落盘** | `save()` 每次 `JSON.stringify(core.S)` | npcs + memories + knowledge 一起膨胀，每次几 MB | **第二杠杆** → 存档分片 |
| 位置物化 `npcTick` | 每天 13 次全表遍历（`syncOne` 里 `tier < 1` 已提前 return） | 约 13 × 200 次 `npcAt` 调用 | **收益小** → Phase 4 的位置部分可以最后做 |
| 在场查询 `presentNPCs` | 已于 Phase 3 加索引 | O(1) | 已解决 |
| 事件配额 / 随机流 | 已于 Phase 1/2 解决 | 与 NPC 数解耦 | 已解决 |

**所以执行顺序不是方案原文的 4→6→7，而是 6 → 存档分片 → 4 → 7。**

还有一条重要事实：`npcAt(id, s)` 是**纯函数**（世界书 + 时间 + 门禁位），位置是按需算出来的；
`NpcDynamic.curLoc` 只是它的物化缓存，全仓消费者仅 4 处（`ai/ContextBuilder.ts` ×2、`ai/ConsequencePlanner.ts` ×1、`world/index.ts` 导出）。
所以「位置」这件事本来就不需要 tick——真正需要 tick 的是**记忆与关系**。

## 2. Phase 6 · 记忆分级（先做，最大杠杆）

### 2.1 现状

`src/memory/lifecycle/MemoryLifecycle.ts` 的 `memoryTick(s, day)` 每天对**每个 owner 的每条记忆**跑 `decayTick`（衰减 + 遗忘 + 归并）。
它由 `src/plugins/daySettle.ts` 的顺序表（第 5 步）驱动。

### 2.2 要做的

按 NPC 与玩家的关联度分频处理——**判据用「关联度」而不是距离**，因为文字 RPG 里「远处但有关系的人」比「同城路人」更值得被记住：

| 层 | 判据（用现有数据，不需要新字段） | 处理频率 | 记忆保留 |
|---|---|---|---|
| **L0 相关** | `s.npcs[id]` 存在，且 `att !== 0` 或 `met` 或当天有过交互 | 每天 | 全量（现状不变） |
| **L1 接触过** | `s.npcs[id]` 存在，但无上述关联 | 每 3 天 | 全量 |
| **L2 未接触** | `s.npcs[id]` 不存在（从未投影过） | 每 7 天 | 只留长期摘要 |

判据为什么干净：**「有 `NpcDynamic` 条目」本身就意味着「曾被玩家触及」**——条目是 `npcDyn()` 惰性建出来的，不是世界书预置的。

### 2.3 落点

- `MemoryLifecycle.ts`：`memoryTick` 加一层分发，按 owner 的层决定 `day % period === 0` 才处理；L2 只跑归并（不跑逐条衰减）。
- 层判定抽成一个导出函数 `memoryLodOf(ownerId, s)`，**单独可测**（这是全部逻辑的核心，必须有直接用例）。
- `daySettle.ts` 顺序表的第 5 步不变（仍调 `memoryTick`）——分频逻辑在记忆模块内部，不要泄漏到顺序表。

### 2.4 验收

- 新增用例：同一个 owner 在 L0/L1/L2 三种状态下，连续 7 天 tick 的处理次数分别是 7 / 2–3 / 1。
- 现有 `memory-engine.test.ts`（710 行）必须全绿——它覆盖记忆的衰减与归并语义，改动不能动这些语义，**只动「多久跑一次」**。

## 3. 存档分片（第二杠杆，独立可做）

### 3.1 现状

`src/world/WorldState.ts` 的 `save()` 每次把整个 `core.S` 序列化；`src/repo/index.ts` 与 `src/repo/sqlite.ts` 各存一份整档。

### 3.2 要做的

把三张随 NPC 增长的表拆成独立存储键，**只写变化过的分片**：

```
saves/main         —— 除下面三张表之外的一切（player / rep / econ / cases / dungeon / …）
saves/npcs         —— npcs（含 curLoc / goal / bag / gold）
saves/memories     —— memories + beliefs
saves/knowledge    —— knowledge（感知表）+ cases
```

**照抄现成的模式**：`SavePort` 上已经有 `loadVectors/saveVectors` 与 `loadWorldLog/saveWorldLog` 两对可选通道，分片照这个形状加，介质不支持时静默退化为整档。

### 3.3 关键约束

- **`hydrate` 的兜底链不能动**：分片读取失败时要能回落到「该表为空」而不是整档报废。
- **`validateState` 仍是唯一闸门**：分片加载后拼出的 state 必须走同一道校验（不要在分片层另开校验）。
- 旧档（整档格式）必须可读——迁移策略是「读时兼容、写时新格式」。

### 3.4 验收

- `repo/sqlite.test.ts` 补分片往返用例（含「只改 npcs → 只写 npcs」的断言）。
- 用一份 200 NPC 的合成档测落盘耗时与体积，与整档对比（这是这个 Phase 唯一的量化目标）。

## 4. Phase 4 · 状态 tick 分层（在 Phase 6 之后）

### 4.1 先做「状态」，后做「位置」

Phase 6 做完之后，**还需要每天 tick 的状态**就剩：关系衰减（`Bond.ts` 的 `bondDailyTick`）、NPC 目标（`goal`）、NPC 侧钱物。
它们的处理频率应当与记忆用**同一套层判据**——建议把 `memoryLodOf` 提成通用 `lodOfNpc(id, s)`，两处共用（一份判据，两处消费）。

### 4.2 位置去物化（收益小，但能删一个冗余字段）

`NpcDynamic.curLoc` 是 `npcAt()` 的物化缓存，消费者只有 4 处。
要删的话：① `npcCurLoc(id, s)` 改为直接返回 `npcAt(id, s)`；② 删 `Autonomy.ts` 的 `syncOne` / `npcTick`；③ `daySettle` 的第 13 步与 `hour_advanced` 订阅一并撤掉；④ `cardD1.test.ts` 有 9 处断言要改。

**注意**：`npcCurLoc` 的现有语义是「优先物化视图，回落即时计算」，删掉物化后行为等价（因为物化本来就是纯函数的缓存），但**要确认没有代码依赖「`curLoc` 这个字段存在」**（例如存档校验或 UI 面板）。

## 5. Phase 7 · L2 聚合（需要产品设计，最后做）

这一步的**技术骨架明确、内容判据不明**——它依赖「哪些 NPC 需要个体身份」这个产品决策，所以我没有替它拍板。

### 5.1 骨架

```ts
interface AggregateState {
  id: string;          // 'village_stonebridge' 之类
  population: number;
  unrest: number;      // 0–100
  food: number;
  majorEvents: string[];  // 最近影响过它的事件 id（沿因果链可查）
}
```

落在 `WorldState.aggregates?: Record<string, AggregateState>`，`hydrate` 补空表。

### 5.2 需要先定的判据

「谁需要个体身份」这条决定展开/折叠的边界。建议的默认规则（**需要你确认或改写**）：

- 世界书 `people.json` 里有名有姓的（15 个）→ **永远个体**，不参与聚合
- 由 `data/world/` 的其他表批量生成的背景人口 → **聚合**
- 被事件提名过的（出现在任何 `WorldEvent.target` 里）→ 从聚合**升级为个体**（沿因果链可查，这是现成的：`worldEventLog.byId`）

### 5.3 与既有设计的接续

聚合状态应当由 `worldBus` 上的 L2/L3 事件驱动（`faction_relation_changed`、`city_at_war` 之类），而不是新开一条更新通道——否则又会变成「第二个事实来源」。

## 6. 已知的坑（这一路真金白银换来的，别重踩）

1. **改测试时不要用「恰好命中」支撑断言**。我犯过一次：把 `arch-e2e` 的目击用例从 `rng.inject` 改成 `injectSampling` 时顺手把玩家挪去了洞窟——全库没有 NPC 会到洞窟，注入点成了**死代码**，测试绿了但覆盖被换掉。审查逮到的。**构造场景要用规则手段，并加前置断言**（如「在场者 > 0」）。
2. **改随机流长度会连带影响一批测试**。Phase 2 让 `witnessesOf` 不再消耗 rng，两处测试立刻红——因为它们依赖「随机流的第几个值」。凡是要动随机流的地方，先 grep 一遍 `rng.inject` / `rng.seed` 的用法。
3. **提升能力会让清单断言变红，那是正确的红**。`arch-integration` 的 `NO_MODEL` 集合与「可调用系统集合」是钉死的；提升能力时同步期望即可，不要放宽断言。
4. **`mutate.playerBag` / `npcBag` 的「转出」在库存不足时仍返回 `true`**（沿用了 `Gains.removeItem` 的语义：减到 ≤0 就删行）。转移类处理器必须**自己判足额**，否则会把「转出 99 件而对方只有 3 件」执行成「凭空造出 99 件」。
5. **时空约束只该把已存在的规则显式化**，凭空发明门槛会误伤（试过给 `grant_title` 加 `minLevel: 2`，被新局用例当场打回）。
6. **门禁命令：显式收集四码 + 错误取头部**。见 §0 第 3 条。
7. **`subscribe()` 是覆盖式注册**：同一系统只能调一次，多个事件类型必须合并进同一次调用（`codex` 用 `data.mode` 分派、`relationship` 用 `e.type` 分派，照抄）。
