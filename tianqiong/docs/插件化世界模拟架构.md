# 插件化世界模拟架构（落地说明）

> 依据：《AI驱动文字RPG：插件化世界模拟架构设计与实施方案》
> 本文只写**已经落地**的东西与**真实契约**；未落地的在 §6 明确列出。
> 改动 `src/world` `src/events` `src/actions` `src/dice` `src/validation` `src/plugins` `src/execution` `src/systems` 前必读。

## 0. 一句话

**系统负责事实与规则，World API 负责统一读写，Event Bus 负责传播事件，World State 记录世界事实，
骰子负责随机性，AI 负责复杂因果推演，Executor 负责安全执行 AI 提出的后果。**

**依赖方向（eslint 强制，违反即 lint 失败）**


引擎层禁止依赖 React / Zustand / UI / store；内容权威层（types/data）零依赖。

## 2. 两个总线，必须分清

| 通道 | 用途 | 特征 |
|---|---|---|
| `bus`（EventBus.ts） | 引擎 → 界面 的信号 | CoreEvent：changed / toast / check / screen / combat…，给界面看的 |
| `worldBus`（EventBus.ts） | 系统 ↔ 系统 的世界事实 | WorldEvent：可追溯、可分级、可防环，给推演用的 |

**铁律 §21**：系统之间不点对点调用，只发事件让相关方自行决定是否响应。
**铁律 §22**：Action ≠ Event。玩家「想做什么」是 Action；世界「已经发生了什么」才是 Event。
`addRep` 只有在声望**真的变了**（未被夹取到同值）时才发布 `reputation_changed`。

## 3. 七大基础设施

### 3.1 World API（§4）—— `src/world/WorldAPI.ts`

```ts
import { world } from '@/world';

world.query.get_character('lita');   // 只读
world.query.get_time();              // { tick, day, year, month, date, hour, period, weather }
world.query.get_capabilities();      // §20 可调用能力列表（只含可执行动作）
world.query.get_declared_capabilities(); // 全部声明（含 internal，供面板与审计）
world.query.get_recent_checks();     // §44 最近检定留痕（骰值可追溯）
world.command({ type: 'travel', loc: 'tavern' });   // UI 命令通道
world.execute({                     // §4.2 世界动词通道（外部脚本 / AI 同一条路）
  action: 'change_reputation', target: 'empire', source: 'empire',
  reason: 'quest_reward', params: { delta: 5 },
});
```

设计约束：本文件**只依赖 WorldState / WorldClock / 世界书 / 契约类型**，不 import 任何具体系统——
世界门面因此不可能与系统插件构成循环依赖。

**两条修改通道（§4.2）**：
`command()` 接 UI 的 `GameCommand` 枚举；`execute()` 接世界动词（= capabilities 里登记的动作名），
内部构造单条后果计划交给 `WorldExecutor` —— 因此**与 AI 推演走完全相同的验证与执行路径**，
不存在绕过 Validator 的后门（§18）。可行动词以 `plugins/systems.ts` 的白名单为准。

**动作契约**：`target` 是**受影响的实体**，规则表条目（称号 id / 罪名 / 事件类型）一律走 `params`。
这条约定来自一次真实的验证器拦截：早期把称号 id 塞进 target，被实体存在性检查当场拒绝。

### 3.2 EventSchema + worldBus（§5/§6/§12/§30/§31/§32）

```ts
import { worldBus } from '@/events/EventBus';
import { makeEvent, levelOf } from '@/events/EventSchema';

worldBus.on('character_died', (e) => { /* 响应 */ }, 'my-system');
worldBus.emit(makeEvent({ type: 'character_died', day: 3, target: 'merchant_01', cause: 'poison' }));
worldBus.schedule(makeEvent({ type: 'city_at_war', day: 10 }), 3);  // 3 天后到期
worldBus.due(day);        // 取出到期计划事件
worldBus.beginTick();     // 新 tick：重置事件风暴配额（dispatch 已自动调用）
```

事件字段（§6 + §29）：`id / type / day / tick / level / actor / target / location / cause /
witnesses / data / parentId / sourceId / processedBy`。

**分级（§12）**：L0 内部账目（不入世界史）· L1 局部 · L2 跨系统 · L3 复杂世界。
分级是**默认值而非天花板**：L3 无条件进推演；L2 里「死/失踪的是有名有姓的人」也升格进推演
（`WorldReasoner` 的 ESCALATIONS 表）——玩家砍翻一头野狼仍是局部事件。
**派发顺序契约**：通配订阅者（`*`：感知 / 世界史 / 审计这类横切关注点）**先于**具体类型订阅者。
顺序反过来时，任何「订阅具体类型却依赖通配订阅者先写入」的插件都会静默失效——目击者插件
正是踩过这个坑（它在感知层登记目击者之前就查了感知表，于是永久早退）。跨订阅类别的顺序有回归护栏。
**防循环（§30）**：`processedBy` 保证同一处理器不重复消费同一事件；单 tick 上限 `MAX_EVENTS_PER_TICK`；
因果深度由 `causality.withParent` 的嵌套层数自动累加，超过 `MAX_CHAIN_DEPTH` 直接进死信队列。
**订阅侧（§21/§34）**：`plugins/subscriptions.ts` 是业务系统订阅的唯一装配点。当前三条：
`quest × character_died`（击杀推进委托，替代原先 Combat→Quests 的直接调用）、
`law × crime_committed`（有人目击即立案）、`economy × large_trade`（大额交易推动品类物价）。
**注意**：订阅是覆盖式注册，必须在能力登记之后装配，否则会顶掉白名单。

**可追溯（§29/§44）**：`WorldExecutor` 执行计划时把 `plan.triggerEvent` 设为因果父，
执行期间各系统发布的事件自动挂到它下面——`worldEventLog.chain(eventId)` 因此能沿 `parentId`
还原「这个 NPC 为什么恨玩家」。

### 3.3 DiceEngine（§9/§10）—— `src/dice/DiceEngine.ts`

```ts
resolveCheck({ type: 'stealth', attribute: 72, difficulty: 60, dice: '1d20', modifier: 0 });
// → { roll, rolls, modifier, total, difficulty, result, margin }
//   result: critical_success | success | failure | critical_failure
```

判定次序与原型 `check()` 一致：自然满点必成、自然 1 必败、雨天 -1。
**铁律 §9**：AI 不得生成骰子结果；一切随机经 `rng` / DiceEngine。
`CheckResolver.check()`（带演出的检定）已改为**委托** DiceEngine 计算，
只保留检定卡演出与收束回调——6 个调用它的系统因此自动走上统一随机入口。

### 3.4 PluginRegistry + CapabilityRegistry（§19/§20）

```ts
plugins.register({
  id: 'combat', version: '1.0.0',
  capabilities: ['start_combat', 'attack'],
  subscribes: ['character_died'],
  handleEvent: (e) => { /* 幂等由 worldBus 保证 */ },
});
```

既有系统的能力在 `src/plugins/systems.ts` 登记，由组合根 `main.tsx` 调 `registerCoreSystems()` 生效。
登记分两级：**effects**（可被后果计划驱动，**每一条都必须有执行器处理器**）与 **internal**
（玩家操作 / 战斗裁定 / 纯工具——面板与审计可见，但 AI 不能直接驱动，否则等于替玩家做决定）。
两者的一致性由 `arch-infra.test.ts` 的双向守卫用例钉死：`effects ⇔ worldExecutor.actions()`。
声明能力却没人执行它，就是白名单在撒谎——这条守卫专防这个（审计整改时正是它暴露出 38 条空洞）。

### 3.5 Rule Validator 双闸（§16/§42）

```ts
validatePlan(raw)   // 形状（SchemaValidator）→ 权限与合法（PermissionValidator）
```

第二闸逐条回答 §16 的问题：动作是否已被某系统注册能力？实体是否存在？数值是否越界？
是否重复执行？依据（`reason`）是否齐备？**任一不过 = 整份计划拒绝执行**，不做部分猜测。

### 3.6 WorldExecutor（§17）—— `src/execution/WorldExecutor.ts`

```ts
worldExecutor.registerHandler('change_reputation', (a, plan) => { /* 真正落地 */ });
worldExecutor.execute(plan);   // → { executed, rejected, outcomes, newEvents }
```

执行器**不认识任何具体系统**：新增系统只需注册处理器，不必改执行器。
处理器装配集中在 `plugins/handlers.ts`（组合根与测试共用），当前覆盖 20 条可执行动作
（立案 / 声望 / 好感 / NPC 目标 / 委托四态 / 物品 / 金钱 / 称号 / 犯罪 / 事件三动词…）。

**上下文只下发可执行动作**：`ContextBuilder` 用 `plugins.executableMap()` 而不是全量
`capabilityMap()`——把做不到的动作写进提示词，等于主动引导模型产出必然被拒的计划。
执行期间由各系统发布的世界事件被收集进 `newEvents`，形成 §47 的回合闭环。

### 3.7 World Reasoner（§13/§35/§47）—— `src/ai/WorldReasoner.ts`

```
事件(L3 / 升格后的 L2) → ContextBuilder(最小上下文) → ReasonerPort(AI) → ConsequencePlanner(严格 JSON)
        → Rule Validator → WorldExecutor → World State → 新事件 → worldBus
```

```ts
setReasonerPort({ id: 'llm', reason: (ctx) => fetchPlan(ctx) });
await reasonAbout(event);     // 端口未注入时完全空转，零副作用
attachReasoner();             // 可选：自动订阅合格事件（缺省不启用；推演产物不再触发推演）
```

**铁律 §18**：AI 不直接改数据库、不直接改状态。**§42**：解析失败 = 拒绝执行，绝不猜测。

**规则推演兜底（§11 精神）**：`ai/ruleReasoner.ts` 是与 `ruleSim` 同构的无模型通道——
真实模型不可用时，由规则从上下文推导有依据的后果（命案有目击者 → 势力立案；亲族 → 追凶目标；
罪案被目击 → 势力敌意）。**找不到依据就不推演**（§25），每条后果绑定 `triggerEvent/reason/source`（§26）。
组合根已 `setReasonerPort(ruleReasoner)` 并 `attachReasoner()`——接入真实模型时换端口即可。

### 3.8 NPC 感知层（§8）—— `src/events/Perception.ts`

**世界真相 ≠ NPC 认知**。世界史（`worldEventLog`）记客观事实；感知表记「谁知道了什么」。

```ts
registerPerception(event, state);      // 按在场 NPC × 事件显眼度判定目击者并登记
witnessesOf(event, state);             // 只判定不登记
spreadPerception(eventId, from, to, 0.6);  // 消息传播：每经一手保真度衰减，<0.15 自行中断
knownBy('lita');                       // 该 NPC 知道的事实（亲历 / 听说，含保真度）
perception.knowers(eventId);           // 「谁泄露了消息」类调查
attachPerception();                    // 组合根挂载；未挂载时完全空转
```

- 显眼度表决定察觉概率：当街死人 0.9、街头犯罪 0.45、偷窃 0.2；未登记类型默认 0.5。
  好感变化显眼度为 **0**：那是两个人的私事，旁人不该「目击」到别人心里的秤。
- 亲历优先：已听说的事遇到亲历时升级为亲历，不会被传闻覆盖。
- **随存档持久化**：感知表存在 `WorldState.knowledge`（每 NPC 上限 40 条；记忆表另有自己的容量规则），
  旧档经 `hydrate` 补空表——「没人知道任何事」是安全的默认。
- 喂 AI 推演时用 `perceiveContext(npcId)` 而不是世界真相——这样才有谣言、误会、怀疑与信息不对称。

### 3.9 调查与证据（§8 / §36）—— `src/systems/law/Investigation.ts`

感知层的下游：**没人看见就没有案子**。

```ts
openCase(event, filedBy);   // 立案：证据只能来自感知表（perception.knowers）
investigationTick(state);   // 每日取证推进（挂 WorldClock.newDay）
caseView();                 // 在办 / 已结案件总览；进度满 → 结案（通缉 + 势力敌意）
```

推演产出的 `start_investigation` 后果由组合根接到 `openCase`——形成
「事件 → 感知 → 推演 → 验证 → 执行 → 案件 → 结案」的完整闭环（§17/§47）。

## 4. 怎么新增一个系统（§45 正道）

1. 在 `src/systems/<领域>/` 写实现，状态改写经 `world/WorldState`，对外只发 `worldBus` 事件。
2. 在 `src/plugins/systems.ts` 登记 `id / version / capabilities / subscribes`。
3. 需要响应后果计划时，在组合根 `worldExecutor.registerHandler('<能力名>', fn)`。
4. 补测试（`src/tests/`），跑四绿。

**不要**：改 NPC 系统去通知任务系统；在 20 个 if/else 里加分支；让 AI 直接写状态。

## 5. 数据流（§47）

```
玩家输入 → ActionParser → 对应 System → Rule Check → (需要随机? DiceEngine)
        → World API → World State → 产生 Event → worldBus → 相关系统响应
        → 是否复杂世界事件(L3)?
            否 → 结束 / 等下一 Tick
            是 → ContextBuilder → World Reasoner → Consequence Plan
               → Rule Validator → World Executor → World API → World State → 新事件
```

## 6. 现状盘点（诚实清单）

**已落地**

- §4 World API 统一门面（查询只读 + command 唯一入口）
- §5/§6/§29/§30/§31/§32 世界事件总线、标准事件结构、分级、防环、计划事件、事件日志
- §8 NPC 感知分离（亲历 / 传闻 / 保真度衰减 / 显眼度判定）+ **感知持久化** + **调查证据链**
- §9/§10 DiceEngine 与 resolveCheck 契约
- §11 规则推演兜底 / §12 事件分级表（L0–L3）/ §13 **LLM 推演端口与混合装配**
- §13–§18 World Reasoner 闭环（ContextBuilder / ConsequencePlanner / Validator / Executor）
- §19/§20 插件与能力注册（19 个既有系统登记能力白名单）
- **§16/§17 能力与执行器同源**：能力表拆 effects / internal，Validator 只放行已接入执行器的动作，
  提示词同样只下发可执行项；双向守卫测试钉死 `effects ⇔ worldExecutor.actions()`
- **§12/§23 命案升格**：分级是默认值而非天花板——`character_died` / `npc_missing` 的 target
  若是有名有姓的人（世界书或运行时 NPC 表命中），L2 也进推演；砍翻野狼仍是局部事件。
  这是 `ruleReasoner.onDeath`（立案 / 追凶 / 委托受阻）第一次在真实装配下可达
- §22/§34 系统接入：声望、好感、击杀、任务交付、立案、制作、大额交易、称号
- §31/§32/§36 World Clock 日边界结算计划事件 + 案件取证推进
- **L3 事件源**：星渊裂隙临界 → `abyss_breach`，可真正唤起推演通道
- **推演护栏（§30）**：推演自己造出来的事实不再触发推演——判定按**事件来源**
  （`WorldEvent.origin = 'reasoner'`，在事件**创建时**打上），而不是「执行期因果深度」：
    · 深度判定漏掉 `schedule_event` 排的延迟事件（隔天发布时深度早已归零，跨日自激拦不住）；
    · 深度判定还会误杀外部脚本经 `world.execute` 注入的合法 L3 事实（它不带来源标记）。
  外加 in-flight 上限与 `reasonerStats()`（跳过多少轮可查），模型无法用 `create_event` /
  `schedule_event` 自造事实把推演递归放大
- **死信留痕（§30）**：超配额或因果链过深的事件不再静默消失，组合根挂的观察者
  会把「某某事件未扩散」写进世界日志（`attachDeadLetterWatch`）
- **§44 检定留痕**：每次检定的骰值/难度/成败进 `WorldState.checks`（环形 30 条）——
  「这一下是怎么判的」在存档里答得出来（此前骰值只发给 UI 的检定卡）
- **装配自检**：`registerConsequenceHandlers()` 末尾校验每个处理器都已在能力表里
  声明为可执行（与守卫测试互补：一边看静态同源，一边挡运行时的反向空洞）
- §40 目录结构、§41 架构测试、§42 严格 JSON 契约
- **§44 事实来源**：世界事件带 actor/target/location/cause/data；后果执行期间产生的事件
  自动带 `parentId`（因果链真正连得上）；`change_goal` 落点保留 `sourceEvent`；
  案件与事件日志可沿因果链向上追溯

**已知边界（当前实现范围，不是待办清单）**

- 三个预留的分类/字段见 §6.5。分类是真参与运行时判断的（Validator 放行/拒绝、提示词下发）；
  数据空槽（`effects` / `bag` / `gold`）目前只有类型、存档闸门与 `get_active_effects` 在读，
  写入方要等接入——它们按「用户要求的预留」存在，不是已经有玩法在用的字段
- 感知表每 NPC 上限 40 条，超出丢最旧的；记忆表每角色 80 条，按当前强度淘汰
  （老表的 `compressMem` 分级压缩已退役，容量只剩这一处规则）
- 调查只建模「势力 vs 玩家」的案件；NPC 之间的纠纷尚未纳入
- 传播层已起步但仍薄：业务订阅只有 3 条（quest/law/economy）+ 目击者插件，
  其余 14 个系统的 `subscribes` 仍为空；事件总线目前主要仍是记账通道
- **事件驱动要求装配完整**：未走 `bootstrapWorld` 的调用方（如某些单测）会看到
  「事件发出了但没人响应」——这是传播式的固有前提，新增订阅时须同步检查装配路径
- §4.2 的 20 个动词中 15 个有落点（能过验证且能执行）；5 个明确留在 internal
  （`move_character` NPC 位置由日程驱动 / `transfer_item` `transfer_money` NPC 无物品栏与金钱 /
  `add_status` `remove_status` 玩家非战斗期无状态槽）——**被声明但不能执行的动作会被 Validator 拒绝**，
  不再出现「过了验证却在执行期报无处理器」
- **玩家杀死 NPC 的玩法入口仍缺**：生产端 `character_died` 只由战斗击杀魔物产生
  （`target` 是怪物 id），所以升格规则目前只在有 NPC 死亡事件时可触发——缺的是玩法侧的攻击路径
- 跨系统直接 import 约 103 条（改造未加剧，也一条未减）；~~`WorldClock` 反向依赖 10 个业务系统~~ 已收口——日结算抽到 `plugins/daySettle.ts` 之后，时钟只依赖数据层与事件层。
- 世界史是不入档的环形缓冲（上限 500 条），重启即失去 §29 的长期追溯能力
- LLM 推演端口用 mock 通道覆盖了提取与降级逻辑，未在真实 Key 下端到端跑过
- L3 事件源目前只有星渊裂隙一处；`city_at_war` / `ruler_died` 这类事件需要上层剧情线供给。
  `npc_missing` 全仓零生产者（升格规则已就位，等剧情线开口）
- 文档口径：`world.execute` 的可用动词是 **effects 子集**；internal 动词（玩家操作 / 战斗裁定）
  不经后果计划，玩家侧走 `command() → dispatch()`

## 6.5 预留接入点（当前项目还不存在的功能）

原则：**功能没到，位置先到**——接入时只补内容，不改结构。每一条都写清
「接入点在哪 / 接的时候做什么 / 为什么现在不做」，并且都带一条守卫，防止占位悄悄腐烂。

### 能力表的三分类（§20）

`src/plugins/systems.ts` 把能力分成三类，各自语义不含糊：

| 分类 | 含义 | Validator | 提示词 | 面板 |
| --- | --- | --- | --- | --- |
| `effects` | 可被后果计划驱动，**每条都有处理器** | 放行 | 下发 | 可见 |
| `pending` | 世界后果，接入路径明确，**暂不可驱动** | 拒绝 | 不下发 | 可见 |
| `internal` | 玩家操作 / 战斗裁定 / 工具，**刻意不驱动** | 拒绝 | 不下发 | 可见 |

> ⚠ **已过时**：下面这 11 条**已全部提升为 `effects` 并注册处理器**，当前 `pending` 为空。
> 以 `plugins/systems.ts` 与《架构规范》§4.1 为准；保留原文只为记录当时的判断。

当前 `pending`（11 条，每条都在源码里注明了缺什么）：`add_status` `remove_status`
`transfer_item` `transfer_money` `change_price` `change_faction_relation` `spread_rumor`
`form_grudge` `befriend` `suppress_title` `clear_crime`。（**均已接入执行器**。）

守卫测试盯着三件事：**声明层**同一动作不能既写进 `effects` 又写进 `pending`；
**视图层** `pending` 与 `executable` 交集为空（注册表已把可执行动作挡在待接入视图外）；
**反向**某个待接入动作一旦有了处理器，就说明漏了提升动作，测试直接红。
生产者侧另有一道：`effects` 与执行器处理器双向相等（见 §16/§17 的同源用例）。

### 数据模型空槽

- **NPC 侧物品与金钱**：`NpcDynamic.bag` / `NpcDynamic.gold`（`types/world.ts`）。
  `transfer_item` / `transfer_money` 缺的正是这两个字段——NPC 从来没有过自己的
  物品栏与钱包。字段就位后，接入只需写两个处理器 + 一份种子数据。
- **状态效果**：`StatusEffect` + `PlayerState.effects` / `NpcDynamic.effects`。
  现在只有战斗内状态（`CB.status`，出战斗即清），所以「中毒三天」「祝福持续一日」
  这类世界级状态无处落脚。`world.query.get_active_effects()` 接口已就位（现在恒为空）。
- 三个字段都是**可选**：`hydrate` 不补默认——缺失就等于「这个存档里还没有这回事」，
  因此**读取方要自己兜 undefined**（`get_active_effects` 用可选链示范）。
  与仓库里其它可选字段（`wallet` 之类在 `hydrate` 补默认）的差别是有意的：
  「没有 effects」与「effects 是空数组」在这里语义等价，补默认只会多一份要维护的状态。
  存档闸门已覆盖它们的形状（`RuleValidator.checkNpcs` / `checkEffects`）：类型不对、`gold` 为负、
  `effects` 不是数组都会被拒绝——新字段不能因为"还没接入"就在校验里裸奔。

### 分层模型（§24）

`LlmConfig.tiers`（`light` / `heavy`）+ `resolveTier(tier)`。
每档是一个 `ModelSlot`；**未配置任何档位时返回主模型字段的等价副本**，行为与单模型一致
（三条用例钉住回落契约）。空串按「未配置」处理：档位只写了端点却把 Key 留空，
会沿用主模型的 Key——**跨端点配档位时必须把 Key 一起填上**，否则等于把主服务的 Key 发到别人家。
接入时只需在 `WorldReasoner` 里按事件等级选档 + 面板加两个输入框。
为什么现在不做：「哪级事件走哪档」是成本与产品决策；而**分级依据已经就位**
（`EventSchema.levelOf` + 升格判定，推演准入用的就是它）。

### 接入点已存在、等内容的那些

- **玩家杀死 NPC**：`character_died` 的 context 与升格判定都已就位，缺的是**产量方**——
  战斗系统目前只接受魔物 id（`Combat.ts` 的 `startCombat(mids)`）。接入 = 让战斗能带
  NPC 目标，事件 `target` 填 NPC id（升格会自动生效）。
- **L3 事件源**：`city_at_war` / `ruler_died` / `npc_missing` 等在分级表里，但没有生产者。
  接入 = 剧情线在合适的地方 `worldBus.emit(...)`，或外部脚本走
  `world.execute({ action: 'create_event', params: { type } })`（同一条 Validator → Executor 通道）。
- **时空条件校验（§16）**：`PermissionValidator.validateAction` 是接入点，注释里已逐条标明
  已实现 / 未实现。缺的是**契约定义**——方案没给「某动作只在某时段/某地可做」的数据结构。
- **系统订阅扩充（§34）**：14 个系统的 `subscribes` 仍为空，接入点就是
  `SYSTEM_SPECS[].subscribes` + `registerSystemSubscriptions()`（已有 3 条实例可照抄）。
- **世界史与死信持久化**：接入点是 `SavePort` 的可选通道，照着 `loadVectors` / `saveVectors`
  的模式加一对即可（介质不支持时静默退化为内存）。
- **§23 信念 → 行动规则**：规则表 `data/world/memory.json` 的 `beliefActions.rules` 为空是刻意的，
  匹配机制（`matchBeliefRules`）与「已驱动」标记都已就位并有测试。
