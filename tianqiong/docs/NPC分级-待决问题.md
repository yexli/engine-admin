## 一、项目是什么

**天穹纪元 2.0** —— 世界书驱动的单机 AI 文字角色扮演游戏。技术栈 React + TypeScript + Vite + Tauri。

一条硬边界贯穿全局：

> **恒定归引擎，讲述归 AI。** 世界规则、数值结算与状态演化全部由本地确定性引擎裁定；
> 语言模型只负责把结果讲成人话。**不配任何模型也能完整通关。**

这条边界带来的连锁约束（后文会反复用到）：

- **确定性**：同一存档 + 同一随机种子 = 同一结果。随机流长度不能随实体数量漂移。
- **AI 只出文本与判断**，不能改世界状态；判断要过 core 的白名单校验才能落地。
- **降级可用**：模型不可用时自动回退规则模拟，功能不缺失，只是文字不再自由生成。

## 二、问题是怎么冒出来的

### 2.1 起点：15 个 NPC

项目早期，人间的圣辉城里有 15 个可交互 NPC（酒馆老板娘、公会接待、报童、铁匠……），各带 22 个字段：作息、地点、三档问候、话题、关系网、拒绝方式、说话习惯等。他们彼此之间有 10 条关系边。

### 2.2 扩张：109 份人物档案

后来拿到一批世界书人物档案（Markdown，109 人，约 14.6 万字），体例统一，每人 10 个字段：

> 身份 / 种族·年龄·性别 / 境界 / 外貌 / 性格 / 能力 / 过往 / 现状与目标 / 弱点与把柄 / 持有物

这 109 人是**世界级人物**：皇帝、神殿大祭司、六位主神、魔界七领主、七座星枢塔的守塔人、冒险者公会八位分会会长、古代英雄、创世神话人物。与原先的街头小人物不是一个量级。

### 2.3 现状：124 个 NPC，全都同等对待

109 人已全部接入，每人有完整人设、机制字段、三档问候（327 句）、三条话题。加上街头 15 人，名册共 **124 人**。

**问题在于：引擎对 124 人一视同仁。**

一个酒馆老板和一个神祇，在系统里占用的资源、获得的叙事笔墨、参与的模拟深度，**完全相同**。这在 15 人时无所谓，在 124 人时不成立。

## 三、核心问题：`tier` 字段的历史与死因

数据里有个字段叫 `tier`（重要度档），人人必填。它的来历如下。

### 3.1 原设计：它是**成本分级**，不是叙事分级

开发方案的原文（卡 D1）：

> **控成本**：自主模拟按 NPC `tier` 分级——**tier 0 背景 NPC 纯规则 / 不 tick，tier ≥1 才进日程与关系传播**

> `npcTick(s)` —— 遍历 `tier>=1` 的 NPC，按当前时辰重算并写 `curLoc`（**tier 0 背景 NPC 跳过，控成本**）

风险登记表里写明了它的目的：

> | 自主模拟拖垮移动端性能 | 每刻全量 NPC tick + 物价重算 | 按 tier 分级（**tier0 不 tick**）+ 数量封顶 |

**即：`tier` 的原始语义是「这个 NPC 参不参与每刻的全表模拟」，纯粹为了移动端性能。**

### 3.2 但它从未被真正使用，然后被撤销了

实测三件事：

1. **`tier 0` 从落地起就没用过。** 15 个街头 NPC 的取值为 `tier=1 × 3 人`、`tier=2 × 12 人`——**一个 0 都没有**。
2. **`npcTick` 函数现在零引用**，已不存在。
3. **`curLoc`（它唯一的产物）被明确撤销**，代码里留着墓碑注释：

   > Phase 4.2：原 curLoc（自主行动 tick 物化的地点缓存）已撤——位置是 `npcAt` 的纯函数产物

**撤销的原因**：位置本来就是「世界书 + 当前时辰 + 门禁位」的纯函数产物，物化缓存只会引入一个会过期的第二真相（AI 读到的是「他上一次 tick 时在哪」，而不是此刻在哪）。改成按需求值后，全表 tick 就没有存在意义了。

### 3.3 结果

`tier` 失去了唯一的消费者，成为数据里的化石。目前全代码库**没有任何一处读取它**。

而它仍然是必填字段——所以今年新接入的 109 人也被迫填了值（按境界与身份派生的 1/2/3）。

## 四、另一套已存在的分级：LOD

项目里已经有一套分级机制，**它活着并在跑**：

| 层 | 判据 | 处理周期 | 内容 |
|---|---|---|---|
| L0 相关 | 好感≠0 / 正式见过 / 当天聊过或收过礼 | 每天 | 归并 + 逐条衰减 + 信念推导 |
| L1 接触过 | 有条目但以上都不成立 | 3 天 | 同上 |
| L2 未接触 | 世界书有名有姓，但本局从未被投影 | 7 天 | 只归并，不逐条衰减 |

**判据是「玩家与这个人的关联度」，不是身份或地位。** 设计文档专门解释过为什么：

> 判据用**关联度**而不是距离：文字 RPG 里「远处但有关系的人」比「同城路人」更值得被记住、被 tick。

它的作用是**控制记忆系统的开销**——决定一个 NPC 的记忆多久处理一次。

**关键区别**：LOD 是**动态**的（随玩家行为变化），而 `tier` 是**静态**的（写在数据里）。

## 五、目前所有"密度相关"的杠杆（实测）

| 杠杆 | 现值 | 说明 |
|---|---|---|
| 每人记忆容量 | **80 条** | 超出按强度淘汰 |
| 上下文 Token 预算 | **900 token × 1.6 字/token = 1440 字** | 记忆检索的总预算 |
| 检索档位 | `npc_dialogue` topK **8** / `world_reasoner` topK **12** / `quest` topK **6** | 按场景取不同条数 |
| 事件知情条数 | **6** | `perceiveContext(id, 6)` 固定值 |
| 关系边展开 | **无上限** | `ContextBuilder` 里 `Object.entries(n.rels).map(...)` 全量展开 |
| 关注度分级 | L0/L1/L2 | 见上，动态判据 |
| 命名册规模 | **124 人 / 63 个地点 / 404 条关系边** | 关系网刚补齐，人均 3.7 条 |

**上下文组装的设计原则**（早期架构文档 §43）原文是：

> 只装配「最小必要上下文」……**绝不做 SELECT * 全量喂给 AI**

也就是说：项目从一开始就认"要给 AI 喂多少"是个需要控制的东西，但目前是**按场景一刀切**，没有按"这个人有多重要"分。

## 六、三个候选方向

### 方向 A：恢复 `tier` 的原语义

让 `tier 0` 真正生效：背景 NPC 不进日程、不进关系传播、不产生记忆。

- **优点**：忠于原设计；对性能有实际好处（124 人里可以划一大批进"背景"）
- **代价**：tick 机制已撤销，恢复它等于**倒退**（纯函数模型是更优解）；而且"不进关系传播"会切断刚补好的 404 条关系网
- **遗留疑问**：如果只是"不产生记忆"，那与 LOD 的 L2 有什么区别？

### 方向 B：把 `tier` 改作**叙事密度分级**

重新赋予语义：tier 3 的神祇与帝王在 AI 上下文里拿全景细节（更长的记忆检索、更多知情事件），tier 1 的常民只给摘要。

- **优点**：与 124 人规模配套；"世界级人物值得更多笔墨"是叙事直觉
- **代价**：语义要重新定义（旧注释会误导后来者）；**静态字段无法反映剧情变化**——一个常民可能因为玩家与他深交而变得重要，而 `tier` 永远写死
- **需要回答**：与 LOD 的判据冲突时听谁的？（LOD 说"关联度"，tier 说"身份"）

### 方向 C：废弃 `tier`，另立机制

- **优点**：不留歧义字段；可以按需设计
- **代价**：124 条数据要清理；且要回答"新的判据是什么"

## 七、约束条件（动手前必须满足）

这几条是这个项目的硬约束，任何方案都要过：

1. **确定性**：同一存档 + 同一种子 = 同一结果。随机流长度不能随 NPC 数量漂移（项目曾因"每个事件给每个在场 NPC 抽一次随机"导致玩法数值随人数漂移，后来改成哈希抽样）。
2. **无模型也能玩**：分级机制必须在规则模拟下同样成立，不能依赖 LLM。
3. **架构门禁**：跨系统 import 边被一张冻结基线守住（只减不增，新增要说明为何不能走事件总线）；分层由 ESLint 强制（引擎层禁止依赖 React/UI/store）。
4. **AI 不能改状态**：LLM 只能产出文本与判断，落地要过白名单校验。
5. **存档兼容**：旧档必须能读（此前一次势力拆分就要求写迁移逻辑，把旧的单一势力声望分摊到五个新势力）。
6. **移动端**：Tauri 打包，性能预算不宽裕。
