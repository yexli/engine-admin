> **基线**：commit `b7593c8`（分支 `main`）。复核时四面实测通过：`tsc --noEmit` 0 错、`eslint .` 0 错、`vitest run` 50 文件 / 803 例全绿、分层依赖守卫生效。
> **来源**：《AI驱动文字RPG：插件化世界模拟架构与实施方案》《AI世界模拟架构—Agent开发复核与落地验收方案》两份方案，以及依其执行的只读复核结论。
> **纪律**：每批做完跑一次「§10 回归门禁」，绿了再进下一批；每批一个 commit，出问题单批 `git revert`。

本方案处理复核中**实际命中**的问题。复核判定不命中、或项目已诚实标注为设计边界的事项（11 条 pending、combat 的 effects 为空、感知表容量、世界史环形缓冲等）不在修复范围内，仅在 §12 列出。

## 1. 批准来源与验收标准

**批准来源**：两份方案文档（用户提供）+ 只读复核报告（用户确认后要求整理为本方案）。

**范围**：§7 列出的 12 项任务（G-01 ~ G-12），批次一至五。

**验收标准**（对齐方案二 §35 的 PASS 定义）：

1. `world.command()` 有生产调用且 UI 命令路径全部经它；`world.execute()` 是**外部脚本 / mod 的单条动词入口**，仓内无调用方属预期（由 30 处测试覆盖）。本条措辞在二期 H-02 与之对齐。
2. 引擎层不存在绕过 `world.mutate` 的状态字段直接赋值；该约束由 ESLint 规则强制，`npm run lint` 为机器证据。
3. `WorldClock` 不再 import 任何业务系统；日结算顺序由事件订阅注册顺序保证，并有回归用例钉住。
4. `SYSTEM_SPECS` 的每条 internal 都能回溯到真实入口。
5. 四绿门禁全过，且测试总数不低于 803。
6. 复核报告 §25 的 P0-4 降级为 P1（写入路径已收口，剩余为耦合度问题，见 §9 退役决策）。

**不在验收标准内**：系统间 102 条直调的完全消除。那是事件化改造，属于下一份方案，本方案只做到「直调不再能绕开统一写入原语」。

## 4. TDD 路线

**TDD Route: off / skipped。**
模式 `off`（项目未显式要求 TDD），decision 记为 `skipped`，authority 为项目未声明 strict。
**替代验证姿态**：护栏先行 + post-change 全量回归。即每个改动写不出「先失败的测试」时，先补一条**守卫用例**（项目 `arch-infra.test.ts` 已验证过这个模式有效——它曾一次性暴露 38 条空洞能力），再改实现，最后跑四绿。

这样做的理由：本次改动的主体是**调用路径**而非新增行为，路径类问题用守卫测试表达比用行为测试表达更准确（行为测试会全绿却漏掉路径绕行）。

## 7. 任务分解

### 批次一 · 门面收口（P1，机械替换，风险最低）

#### G-01 · UI 命令入口改走 `world.command`

**位置**：`src/store/useGame.ts:7-8`（import）、`:67`（`cmd: (c) => dispatch(c)`）

**改动**：`import { dispatch } from '@/world'` → `import { world } from '@/world'`；`cmd` 体改为 `world.command(c)`。`dispatch` 的直接 import 保留给同一文件内的其他用途（若有），否则一并删除。

**兼容**：`world.command` 的实现是 `dispatch(cmd)` 的直通包装（`src/world/WorldAPI.ts:184`），行为逐位等价。

**验证**：`arch-infra.test.ts` 已有 `world.command({type:'newGame'})` 与 `world.command({type:'travel'})` 用例；新增一条断言 `useGame.getState().cmd` 的调用落点会经过 `world.command`（可用 spy）。手动：开局→移动→对话，UI 行为不变。

**回滚**：单行改动，`git revert` 批次一即恢复。

#### G-02 · 推演计划入口收口

**位置**：`src/ai/WorldReasoner.ts:156`（`withReasonerOrigin(() => worldExecutor.execute(plan))`）、`src/world/WorldAPI.ts:195`（现有 `execute`）

**问题**：`world.execute` 只接**单条** `ConsequenceAction`（世界动词入口），推演产出的是**多条计划**，因此 `WorldReasoner` 只能直调 `worldExecutor`——WorldAPI 在计划通道上缺一个入口。

**改动**：在 `WorldAPI` 增加 `plan(p: ConsequencePlan): ExecResult`，内部转发 `worldExecutor.execute(p)`；`WorldReasoner:156` 改为调 `world.plan(plan)`。

**约束检查**：`WorldAPI` 的设计约束是「只依赖 WorldState / WorldClock / 世界书 / 契约类型，不 import 任何具体系统」。本次新增只多一个类型 import（`ConsequencePlan`，已在 `PlanSchema` 中导出），`worldExecutor` 已在文件中被 import。约束不破。

**验证**：`arch-integration.test.ts` 的闭环用例（"闭环：事件 → 上下文 → AI → 计划 → 验证 → 执行"）改后仍绿；新增断言 `world.plan` 存在且转发正确。

#### G-03 · UI 查询改走 `world.query`

**位置**：`src/ui/` 16 个文件共 37 处 `core.S` / `core.CB` 直读（`SheetHost` 6、`CombatOverlay` 5、`NewsPanel` 5、`CharPanel` 4、`SceneView` 3，其余 11 个文件各 1–2 处）

**改动分两步**：

**G-03a（默认执行）**：把 `world.query` 已覆盖的读取替换掉——`get_character()` / `get_inventory()` / `get_quests()` / `get_factions()` / `get_time()` / `get_weather()` / `get_history()` / `get_events()` / `get_recent_checks()`。预计覆盖 37 处中的约 15 处。

**兼容**：`world.query` 的 getter 对未开局返回 `null` 或空值，UI 现有判空写法可直接沿用。

**验证**：逐面板手动过一遍（角色/任务/地图/系统/新闻/图鉴 + 商店/对话/战斗/检定/地下城浮层）；`npm run build` 通过。

### 批次二 · 写入收口（P0-4 实质修复）

#### G-04 · WorldAPI 增加受控写入原语 `mutate`

**位置**：`src/world/WorldAPI.ts`（在 `query` 与 `command` 之间新增一块）

**改动**：新增字段级写入原语，全部只做状态改动，**不发事件、不弹 toast**（副作用属于系统语义，留在系统层）：

```ts
mutate: {
  playerHp(v: number): void;          // 夹取到 [0, maxHp]
  playerMp(v: number): void;          // 夹取到 [0, maxMp]
  playerGold(delta: number): void;    // 夹取到 >= 0
  playerExp(delta: number): void;     // 夹取到 >= 0
  playerBag(id: string, qty: number): boolean;  // qty>0 入包并堆叠，qty<0 出包，返回是否成功
  rep(faction: string, delta: number): number;  // 夹取到 [-100,100]，返回变化后值
  npcEntry(id: string): NpcDynamic;   // 惰性建条目（唯一投影点）
  npcAtt(id: string, delta: number): { from: number; to: number };
  pushLog(text: string, cls: LogCls): void;     // 含 logSeq 递增与 70 条上限
}
```

**为什么放在 WorldAPI 而不是 WorldState**：方案二 §5.1 要求"读取与修改都通过统一的 World API 或等价统一访问层"，且方案一 §21 明确允许 `A → World API`。放 WorldState 会被读成"又一个容器方法"，放 WorldAPI 才让系统间调用落在方案允许的通道上。

**为什么不是把每个写操作都做成 effects**：`world.execute` 需要 `reason`、走 `runLog`、经 `causality.withParent`，是给「有因果依据的世界动词」用的。玩法层的高频写入（+1 金币、扣 3 点血）没有因果依据可写，强行套用会让 `reason` 变成填字游戏，也会让每次写入都进运行日志。两层的分工是：**`mutate` 管字段，`execute` 管有依据的世界动词**。

**验证**：新增 `src/tests/arch-mutate.test.ts`，逐方法断言边界（负数、越界、未开局时抛错行为与 `need()` 一致、`pushLog` 的 70 条上限与 `logSeq` 单调性）。

#### G-05 · `Gains` 降为原语调用 + 副作用

**位置**：`src/systems/character/Gains.ts` 的 `log:15`、`gainExp:24`、`gainGold:46`、`addItem:55`、`removeItem:63`、`addRep:78`

| 函数 | 改动 | 保留的副作用 |
|---|---|---|
| `log` | 改调 `world.mutate.pushLog` | 无 |
| `gainExp` | 改调 `world.mutate.playerExp` | exp toast、升级循环、技能习得 |
| `gainGold` | 改调 `world.mutate.playerGold` | 正负 toast |
| `addItem` | 改调 `world.mutate.playerBag` | 获得 toast |
| `removeItem` | 同上（qty 取负） | 返回值语义不变 |
| `addRep` | 改调 `world.mutate.rep` | `reputation_changed` 事件（仅真的变化时） |

**签名全部冻结**。19 个系统的 import 与本文件内的调用一处不动。

**验证**：`arch-e2e.test.ts` 的"移动 → 大额交易 → 犯罪 → 战斗胜利"全链、`arch-integration.test.ts` 的"声望实际变化 → reputation_changed，带前后值与因果依据"、"声望被夹取到同一值 → 不发布事件"三条用例必须保持绿——它们正是本次改动最容易破坏语义的地方。

#### G-06 · `Npcs` 的写入同理收口

**位置**：`src/systems/npc/Npcs.ts` 的 `npcDyn:13`（含关系种子投影）、`adjAtt:67`

**改动**：`npcDyn` 改为 `world.mutate.npcEntry` 的薄封装（关系种子投影逻辑随之迁入原语，保持"单一投影点"这一既有设计）；`adjAtt` 的属性夹取与前后值读改写走 `world.mutate.npcAtt`，事件发布与 toast 留在原处。

**验证**：`arch-perception.test.ts` 与 `chat.test.ts`、`bond.test.ts` 全绿；`WorldAPI.query.get_relationship` 的种子视图行为不变（`arch-infra.test.ts` 有对应用例）。

#### G-07 · ESLint 写入路径守卫

**位置**：`eslint.config.js`（`arch-engine` 块之后新增一块）

**改动**：对 `src/systems/**/*.ts` 增加 `no-restricted-syntax`，禁止对世界状态受管字段直接赋值：

```js
{
  name: 'arch-state-write',
  files: ['src/systems/**/*.ts'],
  rules: {
    'no-restricted-syntax': ['error', {
      selector: "AssignmentExpression[left.object.property.name=/^(gold|exp|hp|mp|bag|rep|log|logSeq)$/]",
      message: '世界状态写入必须经 world.mutate（唯一写入原语）；直接赋值会绕过统一层。',
    }],
  },
}
```

**为什么用 lint 而不是测试**：这类问题无法用行为测试表达——写错了状态，测试只会看到"结果不对"而不是"路径不对"。lint 是唯一能表达"路径约束"的机器守卫，且项目已有先例（分层依赖守卫就是这个模式）。

**验证**：`npm run lint` 必须在改完 G-05/G-06 后为 0 错。**实施顺序上这条规则要先跑一遍现状**，把当前命中点全部列出（预计命中 `Gains` 与 `Npcs` 自身，改造后归零），避免规则上线后一次性报出上百条。

**回滚**：lint 规则与代码改造同批提交，回滚即同时回滚。

### 批次三 · 时钟解耦（P1）

#### G-08 · `WorldClock` 日边界改事件化

**位置**：`src/world/WorldClock.ts:7-20`（10 个业务系统 import）、`:82-144`（`newDay` 实现）

**改动**：

1. `newDay` 内保留天气抽取、`beginTick()`、`due()` 结算，其余 8 个系统的日 tick 调用全部移出。
2. `newDay` 发 `worldBus.emit(makeEvent({type:'new_day', ...}))`，并在 `EventSchema.LEVEL_TABLE` 登记 `new_day: 2`。
3. `src/plugins/subscriptions.ts` 新增 `new_day` 订阅组，按**原调用顺序**注册：economy → bond → abyss → investigation → memory → dungeon → theoselect → title。

**顺序契约怎么保**：`EventBus` 已有"同一类型多个订阅按注册顺序收到"的用例与实现（`arch-infra.test.ts`："事件顺序：同一类型多个订阅按注册顺序收到"）。所以顺序由注册顺序保证，而不是由 `newDay` 里的书写顺序保证——契约从隐式变显式。**新增用例**：断言 `new_day` 的订阅者调用序与基线一致（可用 spy 记录调用次序）。

**风险**：这是本方案风险最高的一项。`newDay` 里有一条被注释标为「R3 顺序」的依赖（经济回归必须在羁绊日 tick 之前）。改前先补顺序断言用例，改后用同一用例验证。

**验证**：`time.test.ts`、`cardH4`/`cardH5`/`cardH6`/`cardI2` 全绿；新增 `new_day` 订阅序用例；手动跨日（休息到天亮）观察物价回归、羁绊、案件三条链。

**退役**：`WorldClock` 中 10 个 `@/systems/*` 与 `@/memory/*` 的 import 全部删除。这是本方案唯一一条真正的"退役"，退役触发条件就是本任务完成。

### 批次四 · 能力表完整性（P1/P2）

#### G-09 · internal 能力可回溯

**位置**：`src/plugins/systems.ts:27-31`（`SystemSpec` 定义）、`:49-104`（各系统的 internal 清单）

**问题**：28 条 internal 中 24 条在全仓零出现（`travel_to` `open_dialogue` `star_trade` `chat_free` `descend` `academy_enroll` `unlock_lore` …），真实入口是 `WorldRuntime.uiAction()` 的 `data-a` 字符串与 `GameCommand` 枚举，两套命名之间无映射、无守卫。

**改动**：给 `SystemSpec` 增加可选字段 `entries?: string[]`，登记该能力对应的真实入口名（如 `travel` 的 `entries: ['travel', 'go']`、`dungeon` 的 `entries: ['dungeon_enter', 'dungeon_next']`），并把 `internal` 收敛为真实函数名或保留现名 + 补 `entries`。

**守卫**：`arch-infra.test.ts` 新增用例——每条 internal 必须有非空 `entries`，且每个 `entries` 项能在 `WorldRuntime` 的路由中出现。这条守卫把"面板显示的我能做什么"变成可机检的事实。

## 11. 风险与已知不确定

**高**：G-08 的顺序契约。日结算的调用次序有数值层面的隐式依赖（经济回归影响后续所有金额相关判定）。缓解：改前先写顺序断言用例，用同一用例对比改前改后。若断言无法表达，则该任务降级——把`newDay`拆为"时间模块发事件"与"一个显式的日结算装配函数（保留在组合根）"，同样能去掉时钟对业务系统的依赖。

**中**：G-07 的 lint 选择器可能误伤。世界状态的字段名（`gold` / `exp` / `hp` / `rep` 等）在局部变量上也常见（如 `const gold = rng.R(10,40)` 不会命中赋值，但 `obj.hp = ` 在战斗临时对象上会）。缓解：selector 限定到已知状态对象（`core.S` / `s` / `state`），规则上线前先跑一遍现状、逐条确认。

**中**：G-05 改 `addRep` 时容易丢掉"仅真的变化才发事件"的语义。该语义有专门用例（`arch-integration`），改动必须让该用例保持绿而不是绕过它。

**低**：G-02 新增 `world.plan` 会让 `WorldAPI` 的公开面变大。方案一 §4.2 允许 `WorldAPI.query` / `WorldAPI.command` 这类命名自由度，且 `plan` 与 `execute` 同属"世界动词入口"族，不引入新概念。

**不确定**：真实模型（LLM）端到端仍未跑过。本方案不含此项——它需要 API Key 与真实端点，属于另一类验证（方案二 §26 的完整毒性链），不阻塞架构修复。
