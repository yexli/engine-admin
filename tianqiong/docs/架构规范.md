## 1. 分层与依赖

### 1.1 七层

```
types ← data ← [ world | events | actions | dice | validation | plugins | execution | systems | memory ] ← ai / repo ← store ← ui
```

| 层 | 目录 | 允许依赖 | 硬禁止 |
|---|---|---|---|
| ① 领域类型 | `types/` | 无 | 一切 |
| ② 内容权威 | `data/` | types | 任何逻辑、任何上层 |
| ③ 基础设施 + 系统 | `world/ events/ actions/ dice/ validation/ plugins/ execution/ systems/ memory/` | types、data、同层（遵循 §1.2） | React、zustand、DOM、localStorage、ui、store |
| ④ AI / 持久化 | `ai/`、`repo/` | types、data、③（只读） | ui、store；`ai` 不得反向被 ③ 依赖 |
| ⑤ 界面状态 | `store/` | ③、types | 直接改 WorldState |
| ⑥ 表现 | `ui/` | ③（经 `world/index.ts`）、store、data、types | 改 WorldState（只能发命令） |

### 1.2 同层依赖的三条附加规则

1. **`memory/` 是认知层底部**：它依赖 `types`、`data/world/memory.json`、`world/WorldClock`、`systems/npc/Lod`，并反向取用 `events/EventBus|Perception|EventStore`；除这些外不得再向上依赖。
2. **`world/` 不得依赖任何具体系统**（`WorldRuntime` 除外——它是路由中枢，职责就是认识所有系统）。`WorldClock` 只依赖数据层与事件层。
3. **跨系统 import 受冻结基线管控**：`tests/arch-deps.test.ts` 的基线清单是唯一允许的跨系统边集合，新增边必须先改基线并说明理由。当前基线含约 103 条边（未清账）。

### 1.3 已登记的分层例外（合法，但必须留档）

| 例外 | 位置 | 理由 |
|---|---|---|
| `ai/ContextBuilder` → `world/WorldAPI` | ContextBuilder.ts:8 | 推演需要只读门面；WorldAPI 自陈这是唯一一处系统侧反向 import（WorldAPI.ts:9-10） |
| `world/index.ts` 是第二门面 | world/index.ts:9-180 | 重导出上百个系统函数；表现层「只从 index 进引擎」因此允许绕过 `world.query` |
| 循环依赖的解环文件 | `starnet/Towers.ts`（切 StarNet↔Abyss）、`character/Sheet.ts`（切 Chat↔Dialogue）、`Rites.ts:164-167`（避 timeslip↔rites） | 每个解环文件都必须在头部注释写明它解的是哪条环 |

新增例外 = 改本节表格 + 在文件头写明理由。**不允许「为了避免改基线而偷偷直连」。**

## 2. 状态与所有权

### 2.1 唯一事实来源

`WorldState`（types/world.ts:947）挂在 `core.S`；战斗态 `core.CB`（不落档）；商店游标 `core.curShop`。任何模块取状态用 `need()`，未开局时抛错。

### 2.2 写入层：覆盖范围与规范

`world/WorldMutate.ts` 是**受控写入原语**层，当前覆盖 `player` 字段族。规范如下：

1. **有跨系统读者的字段必须走原语**（gold / hp / mp / exp / rep / 位置 / 序号这类的）。理由：原语是「谁改了它」的唯一可审计点。
2. **只有单一读者的二级容器可以就地改**，但容器本身必须由原语创建（`playerGrowth()`、`npcEntry()` 是范例）。
3. **新增状态子域时必须同时决定它的写入口**，并在 §2.3 表里登记「原语」或「就地改 + 单一读者」。没有登记的写入路径视为未规范化。

### 2.4 `player.flags` 专项规范

`flags` 是布尔语义的公共标记场，当前有 23 个以上字面量键散布在 15 个模块，靠前缀约定分家（`theoselect_*`、`star_*`、`city_*`、`msg_*`、`visited_*`、`tk_*`、`continent_*`…）。

**规范**：

1. 新键必须在 `src/data/world/flags.json` 登记：`{ key, owner, kind: 'bool'|'counter'|'once', life: 'ever'|'day'|'until_cleared', note }`。
2. 键名必须带域前缀（`<domain>_<what>`），动态键用固定前缀（`msg_*`、`tk_*`、`visited_*`）。
3. 禁止用 flags 存字符串或数值（`Guild.ts:79-80` 已经明确否决过这种做法）——需要非布尔状态就加正式字段。
4. 登记文件落地后加一条守卫：代码里出现的 flags 字面量键必须在登记表内。

（本条为**新增规范**，登记文件尚未创建，列在 §9.3 待办。）

### 2.5 存档契约

- **`validate(state)` 拒结构错乱，`hydrate(state)` 补字段缺失**，两者互补，任何一侧放宽必须同步另一侧。
- 新字段一律**可选** + `hydrate` 补默认；`ver` 保持 `1`（旧档永远可读是硬承诺）。
- 自增序号（`evtSeq/logSeq/memSeq/isq`）必须随档持久化，且载入时从「档内最大值」续起——不是从 0。
- 分片：`main / npcs / mind / know`；四片齐全才算完整档，指纹不符整份作废并回落上一份完整档。

## 3. 系统规范

### 3.1 准入标准

一个东西要叫「系统」，必须同时满足：

1. 有明确的状态所有权，**或**明确声明为无状态规则模块（写在文件头注释里）
2. 至少有一条对外能力，**或**至少一条事件订阅
3. 能一句话说清「管什么、不管什么」
4. 有确定性测试覆盖
5. 不与其它系统共享同一状态字段的写权限（依 §2.3）

### 3.2 七个域（归属判定用）

| 域 | 系统 | 概念所有权 |
|---|---|---|
| **个体 Actor** | character、combat、reputation、academy | 一个人的属性、成长、对抗与声名 |
| **社交 Social** | npc、dialogue、relationship | 谁在场、怎么说话、彼此什么关系 |
| **财富 Wealth** | inventory、economy | 物品与钱、价与量 |
| **秩序 Order** | law、faction、quest、customs | 规则、组织、契约、习俗与禁忌 |
| **空间 Space** | travel、dungeon、starnet | 位置、远征、网内空间 |
| **信仰与生命 Faith & Life** | religion、timeslip | 神与人的约定、时间与寿数 |
| **世界与宏观 World & Meta** | world_facts | 事实注入 |

> 2026-09 收敛后共 **19 个系统**（原 24 个）。「认知与知识」域因为 codex 并入 academy、naming 降级为规则模块而消失——这不是漏项，是合并的结果，记录见 §9.7。

### 3.3 新增功能的归属流程

1. 它**改变状态**吗？不改变 → 它是规则模块，不进登记表（例：`Monsters`、`Towers` 就该如此）。
2. 它改变的状态属于哪个现有序？**优先并入该域**，不新建系统。
3. 它引入了新的状态子域吗？是 → 在 §2.3 表里加一行并指定所有者（这一步不能省）。
4. 它需要被 AI 的后果计划驱动吗？不需要 → 只登记 `internal` + `entries`。
5. 它只能由时间推进驱动吗？是 → 加进 `daySettle` 顺序表末尾，并补顺序断言。

### 3.4 无状态规则模块（不进登记表）

`naming/Naming.ts`、`dungeon/Monsters.ts`、`starnet/Towers.ts` 属此类：纯函数/纯查询，不读写状态。它们**不是系统**，可以住在 `systems/` 目录里（目录是文件组织，登记表才是契约），但不得登记能力、不得发世界事件。

naming 在 2026-09 收敛中已从登记表移出（原登记 generate_name / validate_name 两条 internal，无 entries、无外部能力消费者——它被 Equip 直接函数调用）。

### 3.5 端口型系统

world_facts 是唯一的端口型系统：它**没有状态域**，登记 create_event / schedule_event / trigger_event 三个动作，作用是让外部脚本与 AI 能把新事实注入世界总线。

它必须留在登记表里——白名单要求每条 effects 都有归属系统，移出会让外部注入通道随白名单一起消失。判断一个登记项是玩法系统还是端口，只看一件事：**它有没有状态域。**

## 4. 能力与事件规范

### 4.1 能力三分类

| 分类 | 含义 | Validator | 提示词 | 面板 |
|---|---|---|---|---|
| `effects` | 可被后果计划驱动，**每条必须有执行器处理器** | 放行 | 下发 | 可见 |
| `pending` | 世界后果、路径明确但暂不可驱动 | 拒绝 | 不下发 | 可见 |
| `internal` | 玩家操作 / 战斗裁定 / 工具，**刻意不驱动** | 拒绝 | 不下发 | 可见 |

- **当前 `pending` 为空**（0 条）——三分类实际是两分类。这是允许的状态，但新增 `pending` 条目必须注明缺什么。
- `effects ⇔ worldExecutor.actions()` 双向相等，由 `arch-infra.test.ts:538` 钉死。
- 声明 `internal` 的能力若有玩家侧入口，**必须登记真实路由名**（`entries`），由守卫断言路由存在。

### 4.2 新增一条可执行能力的步骤

1. 补数据模型（`types/world.ts`，可选字段）
2. 在 `plugins/handlers.ts` 注册处理器
3. 把动作从 `pending` 提升进 `effects`
4. 守卫测试即验证：`effects` 与处理器双向相等

四条一步都不能省——漏第 3 步会被守卫拦下，漏第 1 步会在执行期炸。

### 4.3 事件规范

- **Action ≠ Event**：意图进系统校验，事实才上总线。
- 分级默认值：L0 内部 / L1 局部 / L2 跨系统 / L3 复杂世界；**L2 里「死/失踪的是有名有姓的人」升格进推演**。
- 通道：`critical / semantic / ambient`，默认由 level 推导，`critical` 必须逐条显式声明。
- 系统之间不点对点调用；订阅只在 `plugins/subscriptions.ts` 一处装配（覆盖式注册，必须在能力登记之后）。
- 通配订阅者（感知、世界史）先于具体类型订阅者派发。
- 因果：`parentId` 形成追溯链；推演自造的事实带 `origin='reasoner'`，一跳即止。

### 4.4 两条修改通道

| 通道 | 入口 | 使用者 |
|---|---|---|
| 命令 | `world.command(GameCommand)` → `dispatch` | UI、玩家操作 |
| 世界动词 | `world.execute(action)` / `world.plan(plan)` | 外部脚本、AI 推演 |

两者走**同一套** Validator → Executor 路径，不存在绕过校验的后门。可用动词 = `effects` 子集。

## 6. 装配与生命周期

**装配顺序就是契约**（漏一步世界会静默失去能力，plugins/bootstrap.ts:8-20）：

```
attachRunLog → attachCoreBridge → bootstrapWorld
   ├─ registerCoreSystems（能力登记）
   ├─ registerSystemSubscriptions（订阅，覆盖式，必须在能力之后）
   ├─ registerDaySettle / attachWorldEventLog / attachPerception / attachMemoryEngine
   └─ registerConsequenceHandlers（处理器，末尾自检）
→ setSavePort → restoreVectorIndex → 渲染
```

- 生产与测试必须走**同一条** `bootstrapWorld` 路径；未走装配的调用方会看到「事件发了但没人响应」。
- **日结算顺序表是显式契约**（`plugins/daySettle.ts`），逐位被 `arch-day-settle.test.ts` 钉住；新步骤**追加在末尾**，不改既有位置（改组内随机消耗顺序会静默改变玩法数值）。
- 每步 try/catch 隔离：单步失败不得带走当天其余步骤。
- 卸载走 dispose 链（HMR、重置、测试三处共用）。

## 7. 测试规范

### 7.1 四绿

`npm run typecheck` / `npm run lint` / `npm test` / `npm run build` —— 四项全绿才可提交。

### 7.2 确定性三件套

核心单测必须三件齐全：`rng.seed(n)` + `scheduler.inject(同步)` + `MemorySaveRepository`。

**确定性的定义**：同一种子 + 同一操作 → 同一结果。**不是**「随机序列一字不动」——新玩法接入后跨天序列本就会变（daySettle.ts:117-126 已记录这个判断）。

### 7.3 架构守卫用例（不变量清单）

| 用例 | 守什么 |
|---|---|
| `arch-infra.test.ts` | World API / Dice / Bus / Schema / Plugin / Validator / Executor 的基础契约；`effects ⇔ 处理器` 双向相等；internal 不进计划；entries 指向真实路由 |
| `arch-deps.test.ts` | 跨系统 import 冻结基线；`WorldState` 的业务依赖不许扩大；覆盖动态 import 与副作用 import |
| `arch-api-door.test.ts` | UI 的写入必须经 `world.command`；`world.plan` 与 `world.execute` 共用同一道防火墙 |
| `arch-day-settle.test.ts` | 日结算顺序与每一步的 `why` |
| `arch-constraint.test.ts` | 时空约束（地点 / 境界 / 时段）走同一条通道 |
| `arch-mutate.test.ts` | 状态写入路径（唯一实现点） |
| `arch-perception.test.ts` | 感知分离与系统接入行为 |
| `arch-sampling.test.ts` | 确定性采样不消耗主随机流 |
| `arch-integration.test.ts` / `arch-e2e.test.ts` | 真实装配路径上的世界事件与因果链 |

### 7.4 新增系统的最低覆盖

正常路径 + 边界（金币为 0 / 通缉封顶 / 缺图回退）+ 确定性复现 + 装配路径（必须走 bootstrap，不是自己拼装）。

## 8. 变更流程

### 8.1 改架构前

1. 读本规范，确认改的是哪一层、哪个状态子域。
2. 读目标系统的文件头注释（本项目的设计权威在注释里，不在文档里）。
3. 判断改动是否触碰守卫用例——触碰即意味着改动会修改契约，需要明确写进提交说明。

### 8.2 提交前检查清单

- [ ] 新状态子域已在 §2.3 表登记所有者与写入口
- [ ] 新能力已分类（`effects` 有处理器 / `internal` 有真实入口 / `pending` 注明缺什么）
