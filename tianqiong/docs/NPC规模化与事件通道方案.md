# NPC 规模化与事件通道方案

> **背景**：二期收口后遗留 I2（节律事件占配额）与 I7（emit 无失败反馈）；同时项目要继续加设定与 NPC，
> 目标是**一两百个 NPC**。本方案把这两件事合并处理——因为它们的根子是同一个：**总线没有分级**。
> **来源**：3 条业界成熟做法，见 §2（含出处）。

---

## 1. 先算账：200 个 NPC 时哪里先爆

| 位置 | 现在的成本 | 200 NPC 时 |
|---|---|---|
| `WorldState.save()` | 每次落盘 `JSON.stringify(core.S)` **全量** | npcs + memories + knowledge 三张表一起膨胀，每次写盘几 MB 字符串化。**最先爆的就是它** |
| `presentNPCs(loc)` | 遍历世界书 NPC 表，逐个算 `npcAt`（含 schedule 判定） | O(N)；而 `witnessesOf` **每个事件调它一次** → O(事件 × N) |
| `witnessesOf` 抽样 | 每个事件 × 每个在场 NPC 各抽一次 `rng.chance` | 随机流长度随 NPC 数线性增长 → **玩法数值随人数漂移** |
| `newDay` 全表遍历 | 状态衰减 / 记忆衰减 / 关系衰减 | 全是 O(N)，一天一次尚可，但随 NPC 增长而涨 |
| `worldEventLog` | 500 条环形缓冲 + 每事件 `record` | 与 NPC 数无关，但事件量随 NPC 数涨 |
| `MAX_EVENTS_PER_TICK = 64` | 固定值 | **与 NPC 数量无关**——同样的玩法在 200 NPC 下产生的事件更多，配额先耗尽（这正是 I2） |

**结论**：不是某个函数慢，而是**三处与 N 成正比的设计**——全量序列化、O(N) 在场查询、随 N 增长的随机流。

## 2. 业界三条做法（含出处）

### 2.1 关注度分级（Simulation LOD）——**最重要的一条**

[tachyon-beep/skillpacks · simulation-vs-faking](https://github.com/tachyon-beep/skillpacks/blob/main/plugins/bravos-simulation-tactics/skills/using-simulation-tactics/simulation-vs-faking.md) 把它列为最关键的基础技能：决定「模拟还是假装」的**第一因素**是玩家会多仔细地看它。

它给出的分级与预算：

- **EXTREME**（玩家操控 / 镜头正对 / 被检视）：全模拟，不省
- **HIGH**（屏幕内、可交互）：细节模拟
- **MEDIUM / LOW / 背景**：简化、抽样、聚合

它用饥饿系统举例说明收益：每帧算 → 0.1ms × 100 = 10ms；每 60 秒算一次 → 0.001ms × 100 = 0.1ms。**快 100 倍，而玩家看不出差别**——因为玩家体验的是「他对模拟的感知」，不是模拟本身。

同一思路的工业印证：[RimWorld 社区的 Slower Pawn Tick Rate](https://catalogue.smods.ru/archives/370182)——降低 pawn 的 tick 频率是公认的性能手段。

### 2.2 优先级通道 + 优雅降级（Priority Shedding）

[garnizeh-labs/aetheris-engine · PRIORITY_CHANNELS_DESIGN](https://github.com/garnizeh-labs/aetheris-engine/blob/main/docs/PRIORITY_CHANNELS_DESIGN.md) 把数据面切成逻辑独立、优先级排序的通道，拥塞时**按优先级选择性丢弃或降频**低优先级通道，保住关键通道；它明确说这是把 Kafka 的 topic + 优先级保留搬到实时传输上。

要点有三：**通道是开发者可配置的**、**降级是有序的（先丢最不重要的）**、**丢弃要可观测**。

这条正好是 I2 与 I7 的解：现在总线只有一条通道、一个固定配额，于是「节律消息」和「可丢噪音」抢同一份预算，抢输了就静默消失。

### 2.3 兴趣管理（Interest Management）

MMO 的标准做法：只更新玩家附近的实体。对应到本项目——**只有与玩家同处一地的 NPC 才需要高频模拟与感知判定**，其余按远方处理。

## 3. 方案

### 3.1 第一层 · 事件通道分级（**现在就该做**）

| 通道 | 语义 | 超限时 | 适用 |
|---|---|---|---|
| `critical` | 节律与关键事实 | **不计配额，永不丢** | `hour_advanced` / `new_day` / 状态衰减 |
| `semantic` | 跨系统语义通知 | **延后到下一 tick 重投**（不丢、不静默） | `grudge_formed` / `lore_unlocked` / `rumor_spread` |
| `ambient` | 可丢噪音 | 现有配额语义（进死信） | `npc_moved` 之类 |

配套两件事：

1. **`emit` 返回 `boolean`**（是否当场派发）。生产方对 `false` 留痕——`runLog.warn` 或 toast。I7 的「喊了没人应却不知道」就此消失。
2. **待重投队列**：`semantic` 超限时入队，`beginTick` 时重投（重投仍带原 `id`，靠 `processedBy` 幂等）。

**为什么 critical 可以不计配额**：这类消息的量级是**固定**的（每天 ≤ 12 条节律 + 1 条日边界），不随玩家动作增长，不会失控；而 `ambient` 的量级随玩法波动，才需要配额。

### 3.2 第二层 · NPC 分层模拟（**规模上来前做**）

| 层 | 范围 | 模拟强度 | 感知/记忆 |
|---|---|---|---|
| **L0 在场** | 与玩家同地点（个位数） | 全模拟：每时辰 tick、参与感知抽样、写记忆 | 全量 |
| **L1 同城** | 同城但不在场（几十） | 低频：每天 tick 一次 | **不参与感知抽样**（感知只由事件发生地的在场者决定） |
| **L2 远方** | 其他城市/大陆（一两百） | **不个体模拟**——用聚合模型（势力倾向 + 事件表）表示，只在被事件提名（`target` / `witnesses`）时唤醒 | 只保留摘要 |

**一个现成的便宜**：本项目的 `npcAt(id, s)` 本来就是**纯函数 of (世界书, t, flags)**——位置是按需算出来的，不是持续维护的状态。所以 L2 的 NPC「时刻都在正确的位置」这件事**零成本**，不需要让他们继续跑。这是现有设计的一处优势，方案只是把它明确成分层依据。

### 3.3 第三层 · 数据与索引（规模临界时做）

1. **空间索引**：维护 `loc → Set<npcId>`，在 `npcTick` 时更新。把 `presentNPCs` 从 O(N) 降到 O(在场数)。
2. **确定性哈希抽样**：把 `rng.chance(p)` 换成 `hash(eventId + npcId) < p`。收益是双份的——**零 rng 消耗**（I1 的同类问题从此结构上不可能出现）、**与扫描顺序无关**（可复现、可并行）。
3. **记忆容量分层**：给 L2 的 NPC 保留摘要记忆而非逐条，避免 200 × 80 条把存档撑爆。
4. **存档分片 + 增量写**：把 `npcs` / `memories` / `knowledge` 拆成独立存储键，只写本次变化过的分片。这是 §1 里最先爆的那一项。

## 4. 落地顺序与验收

| 阶段 | 触发时机 | 内容 | 验收 |
|---|---|---|---|
| **1** | 现在 | 通道分级 + `emit` 返回值 + 待重投队列 | I2/I7 关闭；节律消息在配额耗尽时仍送达；新增「配额耗尽 → 语义消息延后不丢」的用例 |
| **2** | 现在 | 确定性哈希抽样替代 rng | 随机流长度与 NPC 数量解耦；同种子同事件序列结果不变 |
| **3** | NPC 到 50 | 空间索引 + 日结算分帧（每天处理 1/4 的 NPC） | `presentNPCs` 不再遍历全表；单次日结算耗时与 NPC 总数解耦 |
| **4** | NPC 到 200 | L2 聚合模型 + 记忆分层 + 存档分片 | 存档体积与落盘耗时不再随 NPC 数线性增长 |

**阶段 1 与 2 现在就该做**，理由不是将来会用上，而是它们**现在就已在付代价**：

- 配额与随机流的问题在 20 个 NPC 时已经存在（I1 就是活例——一个节律事件让主随机流错位）
- 认知/记忆表被噪声挤占的问题也已存在（容量 40 条，每天约 6 条噪声 ≈ 一周挤掉真实目击）

## 5. 与既有架构的接续

这套方案不推翻二期的收口，而是接在它上面：

- **通道分级** = 把 `LEVEL_TABLE` 从「决定是否进世界史」扩展成「决定投递保证」。两者同源（都按事件重要度），不引入新概念。
- **L2 聚合模型** = 与 `EventSchema` 的分级表天然配合：L3 事件唤醒远方，L1 只在本地扩散。
- **确定性哈希** = 与「§9 AI 不得生成骰子结果」一致：随机性归规则层，且**可复现**。

## 6. 不做的事

- **不引入 ECS**：瓶颈不在实体遍历，而在全量序列化与总线无分级。上 ECS 要重写全部系统而收益错位。
- **不做多线程 / Worker 化**：单机文字 RPG 的主线程预算足够；并行化会把「确定性」这条既有资产（种子随机 + 同步调度器）搭进去。
- **不给 L2 做真实个体模拟**：那正是 §2.1 说的过度模拟——玩家永远看不到远方某个 NPC 今天吃了什么。
